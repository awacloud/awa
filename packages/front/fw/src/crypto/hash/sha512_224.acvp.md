# `sha512_224.js` — ACVP / NIST conformance

## Standards

- **Primary**: **NIST FIPS 180-4** — *Secure Hash Standard*, **§5.3.6.1**
  *Initial Hash Value for SHA-512/224*. Truncated SHA-512 variant (same
  compression function, distinct IV, 224-bit output = 28 bytes =
  first 7 words of the SHA-512 state).
- **Secondary**: **NIST SP 800-107 Rev. 1** — *Recommendation for
  Applications Using Approved Hash Algorithms*. SHA-512/224 is approved
  for general use.
- **ACVP**: `references/NIST/ACVP-Server-1.1.0.42/gen-val/json-files/SHA2-512-224-1.0/`

## Implemented algorithm

`sha512_224.factory(sha512)` — minimal wrapper around
`sha512._internal.makeSha(IV_512_224, 7)`. Fully reuses the SHA-512
compression function (see `sha512.acvp.md` — iteration A2 exposed the
parameterizable builder). Block size = **1024 bits** (identical to
SHA-512, required for HMAC-SHA-512/224).

Public API (HMAC-compatible contract):

- `hash(data)` → bitArray of 7 words (224 bits).
- `fn` streaming constructor: `prototype.{blockSize: 1024, update, finalize}` + clone constructor `new fn(other)`.

The IV (`_INIT_512_224`) is computed per FIPS 180-4 §5.3.6:
`H = SHA-512_with_IV_xor_0xa5a5..(ASCII("SHA-512/224"))`. Value derived
**by independent computation and verified** during iteration A3 (see tests).

### Security properties tested

- [x] **IV distinct from SHA-512** — `digest differs from SHA-512 truncated`:
      verifies that `SHA-512/224(msg) ≠ first 7 words of SHA-512(msg)`.
      Security against cross-variant confusion.
- [x] **1024-bit block size** — required for HMAC-SHA-512/224 (HMAC
      operates by blocks of the underlying compression function, not by
      output size).
- [x] **Streaming = one-shot** — multi-chunk + clone constructor.
- [x] **224-bit output length** (7 words × 32 bits).
- [x] **100 × 1000 standard MCT** — chain A=B=C=SEED then iteration
      `MD = SHA(A‖B‖C)` 1000 times; verifies each checkpoint byte-exact.
      Detects any drift in the compression function.
- [ ] **Bit-level AFT (non-byte-aligned)** — 880/1024 vectors filtered
      out because our implementation only absorbs full bytes (limitation
      inherited from sha512.js, see sha512.acvp.md). **P3** — rarely used.
- [x] **LDT (Large Data Test)** — **post-upgrade audit (gap H1)**: tcId=1028
      (1 GiB of repeated `0800e8a621b041c2`) integrated behind `CRYPTO_FULL=1`
      (mirrors the H1 pattern from sha224/256/384/512, previously overlooked
      for the truncated variant). Validates the 64-bit `_length` counter
      per FIPS 180-4 §5.1.1 over ≥ 2³³ bits.

## Known limitations

- **No bit-level AFT**: 880/1024 ACVP vectors (non-byte-aligned)
  filtered out. Limitation inherited from the SHA-512 core.
- ~~**LDT not integrated**~~ — resolved in the post-upgrade audit: tcId=1028 (1 GiB)
  runs under `CRYPTO_FULL=1` byte-exact in ~40 s.
