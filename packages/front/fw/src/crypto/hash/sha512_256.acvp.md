# `sha512_256.js` — ACVP / NIST conformance

## Standards

- **Primary**: **NIST FIPS 180-4** — *Secure Hash Standard*, **§5.3.6.2**
  *Initial Hash Value for SHA-512/256*. Truncated SHA-512 variant
  (same compression function, distinct IV, 256-bit output = 32 bytes
  = first 8 words of the SHA-512 state).
- **Secondary**: **NIST SP 800-185 §4** mentions SHA-512/256 as a
  high-performance alternative to SHA-256 on 64-bit platforms.
- **ACVP**: `references/NIST/ACVP-Server-1.1.0.42/gen-val/json-files/SHA2-512-256-1.0/`

## Implemented algorithm

`sha512_256.factory(sha512)` — minimal wrapper around
`sha512._internal.makeSha(IV_512_256, 8)`. Fully reuses the SHA-512
compression function (see iteration A2). Block size = **1024
bits** (identical to SHA-512, required for HMAC-SHA-512/256).

Public API (HMAC-compatible contract):

- `hash(data)` → bitArray of 8 words (256 bits).
- `fn` streaming constructor: `prototype.{blockSize: 1024, update, finalize}` + clone constructor `new fn(other)`.

The IV (`_INIT_512_256`) is computed per FIPS 180-4 §5.3.6:
`H = SHA-512_with_IV_xor_0xa5a5..(ASCII("SHA-512/256"))`. **Historical
note**: several sources publish an erroneous value for `H_1` (low half
`c84d6b74` vs the correct value `c84c64c2`). Our IV was **derived by
independent computation** during iteration A3, then cross-verified
against the OpenSSL `crypto/sha/sha512.c sha512_256_init` constants.

### Security properties tested

- [x] **IV distinct from SHA-512** — `digest differs from SHA-512 truncated`
      verifies that `SHA-512/256(msg) ≠ first 8 words of SHA-512(msg)`.
      Security against cross-variant confusion.
- [x] **Independently verified byte-exact IV** — the FIPS §5.3.6
      derivation (SHA-512 with IV XOR a5...) reproduces the OpenSSL
      constants; the classic `c84d6b74` error (present in several
      docs and even some online references) does not pass the
      `hash("abc")` test.
- [x] **1024-bit block size** — required for HMAC-SHA-512/256.
- [x] **Streaming = one-shot** — multi-chunk + clone constructor.
- [x] **256-bit output length** (8 words × 32 bits).
- [x] **100 × 1000 alternate MCT** — variant with trim to the seed length
      (3984 bits = 498 bytes); verifies each checkpoint byte-exact.
- [ ] **Exhaustive AFT** — 971/1024 vectors not covered (sub-sampling
      stride ~20). **P3** — already excellent representative coverage.
- [x] **LDT (Large Data Test)** — **post-upgrade audit (gap H1)**: tcId=1026
      (1 GiB of repeated `dda456ef797c268f`) integrated behind `CRYPTO_FULL=1`
      (mirrors the H1 pattern from sha224/256/384/512, previously overlooked
      for the truncated variant). Validates the 64-bit `_length` counter
      per FIPS 180-4 §5.1.1 over ≥ 2³³ bits.

## Known limitations

- **Aggressive AFT sub-sampling**: 53/1024 (≈ 5%). Regular stride ~20 +
  min/max anchors. `_block` code path exercised across all length buckets.
- ~~**LDT not integrated**~~ — resolved in the post-upgrade audit: tcId=1026 (1 GiB)
  runs under `CRYPTO_FULL=1` byte-exact in ~40 s.
- **Performance**: on Bun/Node, SHA-512/256 is not faster than
  SHA-256 (both emulate 64-bit operations in JavaScript). The SHA-512/256
  performance advantage over SHA-256 (cited in NIST SP 800-185) only
  materializes in C/asm with native 64-bit instructions or SHA-NI offload.
