# `sha256.js` — ACVP / NIST conformance

## Standards

- **Primary**: **FIPS 180-4** — *Secure Hash Standard (SHS)*, §6.2 (SHA-256).
- **Secondary**: ACVP — *Automated Cryptographic Validation Protocol*, draft-celi-acvp-sha.
- **ACVP draft**: `references/NIST/ACVP/src/draft-celi-acvp-sha.adoc`
- **Vectors**: `references/NIST/ACVP-Server-1.1.0.42/gen-val/json-files/SHA2-256-1.0/`

## Implemented algorithm

SHA-256 hash (FIPS 180-4 §6.2). API: `sha256.factory(bitArray, utf8)` →
`{ fn, hash(data) }`. `fn` is a streaming constructor
(`update(data)`/`finalize()`/`reset()`); `hash(data)` is the one-shot
version. Input may be a UTF-8 string or a `bitArray`; the
output is a `bitArray` of 8 32-bit words (256 bits). Guard:
`update` rejects messages > 2^53−1 bits (`console.warn` + `false`).
IV (8 × 32-bit) and K (64 × 32-bit) constants frozen at factory time;
`factory().toString()` remains Worker-serializable.

#### AFT sub-sampling strategy (see the audit plan, *Risks & guardrails*)

The SHA2-256 AFT enumerates 512 messages at pseudo-random lengths in `[1720..12144]` bits (all byte-aligned). Strategy:

- **Regular stride**: tcId 1, 9, 17, …, 505, 512 (one in 8) — uniformly covers the range.
- **Anchors**: `min(len)` and `max(len)` explicitly added (already within the regular stride here, by chance).
- **Total integrated**: **67 / 512 AFT + 1 MCT** out of 513 available in testGroups 1+2 + **1 LDT (1 GiB) gated behind `CRYPTO_FULL=1`** (see LDT line below). Default suite ~1 s; ~12 s under `CRYPTO_FULL=1`.
- **LDT (testGroup 3)**: **Iteration H1** — tcId=514 (1 GiB of repeated `12735c605f3d270c`) integrated behind `CRYPTO_FULL=1` (~11 s on Bun + V8 in 1 MiB batches). Explicitly validates the 64-bit `_length` counter from FIPS 180-4 §5.1.1 over ≥ 2³³ bits. The 2/4/8 GiB vectors (tcId 515-517) remain available in the ACVP suite but are not wired up.

### Security properties tested

- [x] **Correct round / message schedule** — covered by 67 byte-aligned AFT spread uniformly across the length range (each AFT exercises the final `_block` + the specific padding).
- [x] **FIPS 180-4 §5.1.1 padding** — implicitly validated by every AFT (varied lengths modulo 512, including the `≥ 448 mod 512` cases that force an extra padding block).
- [x] **Long-chain stability** — alternate MCT: 100,000 consecutive hashes with A/B/C chaining; any byte-level degradation would deviate `resultsArray[j]` at the next checkpoint.
- [x] **Streaming = one-shot** — `chunked update matches one-shot hash` + `clone via constructor preserves state` + `reset returns instance to empty state`.
- [x] **1M-byte stress** — FIPS-180 App. B vector 3 (1,000,000 × 'a') = 7,813 blocks, validates the 64-bit counter and sub-buffering.
- [x] **2^53−1-bit limit** — `update` returns `false` + `console.warn` beyond it (code review, line 68-71).
- [ ] **Side-channel resistance** — not applicable in the strict sense: SHA-256 has no secret input by default. For HMAC-SHA-256 (secret key), timing resistance is handled by [`hmac.js`](./hmac.js) (XOR-accumulated).

## Known limitations

- ~~**LDT not integrated**~~ — resolved in **H1**: tcId=514 (1 GiB) runs under `CRYPTO_FULL=1` and passes byte-exact (~11 s).
- **AFT sub-sampling**: 67/512 (≈ 13%). The 445 unplayed vectors share the same length class (all byte-aligned within `[1720..12144]`) as the 67 retained ones; the probability that a bug manifests *only* on an unsampled case is negligible because the `_block` code path is identical for all (parameterized solely by the pre-final buffer's length).
- **MCT version**: the ACVP suite provides `mctVersion="alternate"` here (introduced 7/2023). The `"standard"` version (which would require `MSG = A||B||C` without truncation) is not tested separately; it corresponds to the case `digestSize × 3 ∈ SupportedMessageLengths`, already covered intrinsically by the AFT (varied lengths including multiples of 256 bits).
