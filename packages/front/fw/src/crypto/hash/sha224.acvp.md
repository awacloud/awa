# `sha224.js` — ACVP / NIST conformance

## Standards

- **Primary**: **FIPS 180-4** — *Secure Hash Standard (SHS)*, §6.3 (SHA-224).
- **Secondary**: ACVP — *Automated Cryptographic Validation Protocol*, draft-celi-acvp-sha.
- **ACVP draft**: `references/NIST/ACVP/src/draft-celi-acvp-sha.adoc`
- **Vectors**: `references/NIST/ACVP-Server-1.1.0.42/gen-val/json-files/SHA2-224-1.0/`

## Implemented algorithm

SHA-224 hash (FIPS 180-4 §6.3). Identical to SHA-256 except for the IV (FIPS 180-4
§5.3.2) and the final truncation (`h.slice(0, 7)` → 224 bits).

**Architecture (post-upgrade audit Finding 1 resolved)**: `factory(sha256)` →
`{ fn, hash }`. Thin wrapper (~14 useful LOC) over
`sha256._internal.makeSha(_INIT_224, 7)`. **Previously**: this module
duplicated the ~80 LOC of the compression function "to preserve
streaming-state independence" — inconsistent with sha512_224/256, which
reuse sha512 via factory injection with no observed bug. Sharing the
`sha.fn` prototype introduces no state coupling (each `new sha.fn()`
has its own `_h / _buffer / _length`).

#### AFT sub-sampling strategy

The SHA2-224 AFT enumerates 512 messages at lengths `[0..65535]` bits — **433/512 tests are non-byte-aligned** (bit-level inputs). Strategy:

- **Regular stride**: tcId 1, 17, 33, …, 497, 512 (one in 16).
- **Edge-case anchors**: `len=0` (tcId=148), `min(len)`, `max(len)`, first tcId for each critical short length (1, 7, 9, 13, 100, 471, 1023 bits).
- **Volume cap**: tests > 32000 bits filtered out (except the `max(len)=65535` anchor, which is kept) to bound the test file size.
- **Total integrated**: **24 / 512 AFT + 1 MCT** out of 513 tests from testGroups 1+2 + **1 LDT (1 GiB) gated behind `CRYPTO_FULL=1`** (see LDT line below).
- **LDT (testGroup 3)**: **Iteration H1** — tcId=514 (1 GiB of repeated `e788c962d3e8ff55`) integrated behind `CRYPTO_FULL=1`. Validates the 64-bit `_length` counter over ≥ 2³³ bits.

Non-byte-aligned vectors are decoded via `bitArray.clamp(ui8_to_ba(bytes), bitLen)`, which follows the ACVP convention (the useful bits are the leftmost MSBs of the last byte).

### Security properties tested

- [x] **Correct round / message schedule** — covered by 24 AFT spread across the length range (including block padding).
- [x] **Bit-level inputs (non-byte-aligned)** — most AFT (433/512) test lengths not a multiple of 8 bits; the retained cases (471, 1023, etc.) validate the clamp + FIPS 180-4 §5.1.1 padding.
- [x] **FIPS 180-4 §5.1.1 padding** — implicitly validated by every AFT (varied lengths, including the critical `≥ 448 mod 512` case that forces an extra padding block).
- [x] **Long-chain stability** — standard MCT: 100,000 consecutive hashes with A/B/C chaining; any byte-level drift deviates `resultsArray[j]`.
- [x] **Streaming = one-shot** — `chunked update matches one-shot`.
- [x] **256→224 truncation** — `digest is 224 bits (7 x 32-bit words)` validates the `slice(0, 7)`.
- [x] **2^53−1-bit limit** — `update` returns `false` + `console.warn` beyond it (code review, line 69-72).
- [ ] **Side-channel resistance** — N/A (no secret input by default; HMAC usage handled by `hmac.js`).

## Known limitations

- ~~**LDT not integrated**~~ — resolved in **H1**: tcId=514 (1 GiB) runs under `CRYPTO_FULL=1` and passes byte-exact.
- **AFT sub-sampling**: 24/512 (≈ 5%). Choice driven by message size (up to 65535 bits = ~8 KB hex each). The retained lengths sample: 0, 1, 7, 9, 13, 100, 471, 1023, and one case every 16 tcId. The 488 unplayed vectors share the same code paths (`_block` is parameterized solely by the pre-final buffer's length).
- **"alternate" MCT version** not tested (ACVP provides `"standard"` here).
