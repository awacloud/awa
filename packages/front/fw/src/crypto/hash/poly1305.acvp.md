# `poly1305.js` — RFC interop conformance

> **STATUS: RFC interop — outside NIST/CAVP validation.**
> Poly1305 is not a FIPS 140-3 approved MAC (NIST/SP 800-38B
> retains CMAC, NIST/FIPS 198-1 retains HMAC). Coverage is exclusively
> RFC 8439 (IETF) — no published NIST ACVP vector. Poly1305 is
> nonetheless mandated by TLS 1.3 (RFC 8446 §B.4 ChaCha20-Poly1305), QUIC
> (RFC 9001), Noise, WireGuard, Signal, OpenSSH.

## Standards

- **Primary**: **RFC 8439** — *ChaCha20 and Poly1305 for IETF
  Protocols* (June 2018, obsoletes RFC 7539). §2.5 *The Poly1305
  Algorithm*, §2.5.2 *Poly1305 Example and Test Vector*, §A.3 (11
  additional vectors).
- **Origin**: Bernstein 2005 — *The Poly1305-AES message-authentication
  code*. RFC 8439 uses the one-time MAC variant without an AES key (IETF
  variant: 32-byte key = `r ‖ s`, with `r` clamped).

## Implemented algorithm

`poly1305.factory()` exposes the Poly1305 one-time MAC (disposable
32-byte key, typically derived from a ChaCha20 keystream, see RFC 8439
§2.6). Public API (`Uint8Array`):

- `mac(key, msg)` → 16-byte tag, or `false` if key ≠ 32 bytes.
  `r` clamping per RFC 8439 §2.5.1:
  `r[3], r[7], r[11], r[15] &= 15`; `r[4], r[8], r[12] &= 252`.
- `verify(key, msg, tag)` → `true | false`. Constant-time comparison
  via `bitArray.equal` or accumulated XOR.

BigInt implementation (modulo p = 2¹³⁰−5).

### Security properties tested

- [x] **Full RFC 8439 §A.3 conformance** — 11/11 byte-exact KAT
      vectors (degenerate r=0/s=0 cases, single-block carry,
      multi-block carry, crossing 2¹³⁰).
- [x] **Constant-time tag comparison** — `verify` rejects via a
      comparison with no early-return; tested via 16 XOR mutations.
- [x] **§2.5.1 r clamping** — implicit in every byte-exact KAT;
      without correct clamping, no vector would pass.
- [x] **Edge cases** — empty message (tag=s), 1-byte sub-block, exact
      16-byte boundary.
- [x] **key/tag length validation** — early return false on 31, 33,
      15, 17 bytes.
- [x] **No `throw`** — `console.warn` + `return false` (reviewed
      lines 51-78).
- [ ] **Reuse of disposable `r,s`** — Poly1305 loses all security
      guarantees if `(r,s)` is reused across messages. **Out of module
      scope**: protection is the responsibility of the AEAD wrapper
      ChaCha20-Poly1305 (see mode/chacha20poly1305.js, which derives a
      distinct `(r,s)` per ChaCha20 nonce).
- [ ] **Strict constant-time (BigInt)** — modular operations on
      native Node/Bun BigInt; not formally CT but the algorithm's
      structure (no data-dependent branch in the hot path) limits
      the leak.

## Known limitations

- **Outside NIST scope** — no ACVP vector. Validation = RFC 8439.
- **One-time MAC**: security depends on the uniqueness of `(r,s)` per
  message. Our module enforces nothing — caller responsibility or
  AEAD wrapper.
- **BigInt not formally constant-time**: see P3 above.
