# `x25519.js` — RFC interop conformance

> **STATUS: RFC interop — outside NIST/CAVP validation.**
> X25519 is not a FIPS 140-3 approved algorithm (NIST/SP 800-186
> retains ECDH P-{224,256,384,521}; Curve25519 / X25519 remains
> outside the scope of FIPS-validated modules despite being widely
> deployed in TLS 1.3, Noise, Signal, OpenSSH, WireGuard). No ACVP
> vector published by NIST. Coverage is exclusively RFC 7748 + Wycheproof.

## Standards

- **Primary**: **RFC 7748** — *Elliptic Curves for Security* (January
  2016), §5 Curve25519 / §5.2 test vectors, §6 Diffie-Hellman, §7
  security considerations.
- **Secondary**: Bernstein 2006 — *Curve25519: new Diffie-Hellman
  speed records*. Wycheproof X25519 (Project Wycheproof, Google).
- **No NIST ACVP vector** — Curve25519/X25519 is not among the
  curves approved by SP 800-186.

## Implemented algorithm

`x25519.factory()` exposes Curve25519 ECDH (variable-base and fixed-base).
Montgomery-ladder implementation (TweetNaCl-derived, 16 limbs of Float64
with carry propagation). Public API (`Uint8Array`):

- `scalarMult(scalar, u)` → 32 bytes (shared secret) or `false` if
  size ≠ 32 bytes. Performs the RFC 7748 §5 clamping
  (`scalar[0] &= 248; scalar[31] &= 127; scalar[31] |= 64`) and masks
  the MSB of `u` (§5 last paragraph).
- `scalarMultBase(scalar)` → `scalarMult(scalar, [9, 0, ..., 0])`.

No explicit validation of low-order points: the product
`scalarMult(scalar, low_order_u)` returns `0...0`. The caller must
check for an all-zero tag if a contributory property is
required (cf. RFC 7748 §6.1, §7).

### Security properties tested

- [x] **RFC 7748 §5.1.5 clamping** — 4 bit-flip vectors absorbed
      (low-3 of byte 0, high-2 of byte 31).
- [x] **MSB masking of u** — identical output with MSB(u)=1 or 0.
- [x] **Deterministic propagation** — iterative 1 and 1000 byte-exact;
      iterative 1M gated by CRYPTO_FULL.
- [x] **Low-order u detection** — 3 vectors (u=0, u=1, u=p-1); all
      return an all-zero shared secret (the caller must check).
- [x] **ECDH symmetry** — 5 random pairs `aB == bA`.
- [x] **Length validation** — early return false on scalar/u ≠ 32 bytes.
- [x] **No `throw`** — `console.warn` + `return false` (review
      lines 154-162 x25519.js).
- [x] **Explicit rejection of low-order pk** — **Iteration G5**: helper
      `isLowOrderPoint(u)` exposed. Compares `u` (canonicalized via `& 0x7f`
      on byte 31 per RFC 7748 §5) constant-time against 7 documented
      low-order u-coords (Bernstein 2006 + Wycheproof + libsodium). Lets
      the caller filter *before* `scalarMult` instead of testing `output
      === 0…0` afterwards. 13 new tests (7 LOPs detected + high-bit
      variant + 2 valid pk + base point + cross-check `scalarMult(scalar, lop) === 0`
      across the 7 + length edge cases).
- [ ] **Strict constant-time** — `_M`/`_S` Float64 + carry, `_sel25519`
      is CT but `_pow2523` uses a fixed addition chain. Acceptable for
      RFC 7748 §A.1's interactive ECDH context; **P3** for CMVP-like
      SCA audit.

## Known limitations

- **Outside NIST scope** — no ACVP equivalent. Validation = RFC
  7748 + Wycheproof + the Curve25519 spec (Bernstein).
- **1,000,000 iter**: the RFC 7748 §5.2 checkpoint only runs under
  `CRYPTO_FULL=1` (~10 min).
- ~~**No automatic rejection of low-order u**~~ — partially resolved in
  G5: `isLowOrderPoint(u)` is available caller-side. `scalarMult` still
  accepts LOPs (RFC 7748 backward compatibility); the caller decides
  whether to reject. Preferable on the authenticated side (TLS 1.3
  (EC)DHE + signature also covers the risk).
- **TweetNaCl-derived, not formally CT**: see P3 above.
